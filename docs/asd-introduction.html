一、要解决的问题

coding agent 的表现 = 模型 × harness × 上下文管理。skill 机制（discovery 常驻、activation 按需的渐进式披露） 是 harness 给模型的"工具箱路由"，但路由本身没有仪表：失败不报错、成本不落账、遵守度无从核对。 具体是五个可观察的失败模式。

P1该触发的没触发 —— 路由失败不可见

触发条件明明匹配，skill 却从未加载，会话结束后没人知道。这类失败 agent 自己不会报告——它不知道自己"忘了"。 要发现它，必须在事后对每个决策点做反事实判断：在当时的上下文里，这个 skill 该不该触发？ 没有工具做这件事，skill 越装越多，路由质量只能靠感觉。

P2token 花在哪了 —— 成本黑盒

同一份工具结果被反复读入（状态未外置）、压缩协议要求的重读、缓存失效、skill 正文与 harness 注入各占多少—— harness 的活体 context 组成视图不落盘，事后无法回溯。实测数据说明不测量就说不清： 某 Qoder 会话 120 个请求、89% 缓存命中；重复注入的 23.7k extra token 里 99.6% 属压缩协议内重读—— 不测量就分不清"协议税"与"真冗余"，治理无从下手。

P3加载了但没做 —— 遵守度不可度量

skill 加载了、playbook 也在上下文里，但编号步骤做了没有？模型自报"已完成"不可信； 带理由的跳过是否合规也无从判定。需要从轨迹逐步判定 covered / partial / skipped， 且覆盖率必须由判定重算，而不是采信模型自己的说法。

P4调用链断裂 —— 全景不可见

子代理里加载的 skill 归因到谁？Qoder transcript 的派发链是内联 sidechain，主时间线看不见； IDE 通道的子代理日志另存一个 SQLite。不做 join，派发就是孤儿，实际 skill 调用树就是断的—— 正式加载（Skill 工具）与直读（拿文件工具读 SKILL.md 绕过机制）两条通道混在一起，更难看清。

P5病根在 catalog —— 规则层不可诊断

个案审计说"这个 skill 没被路由"，病根却常在 catalog 本身：description 冗长稀释信噪比、过短无法路由、 体量超标导致每次激活都交重税。而且个案太散——要纠规则不纠个案，需要跨会话聚合的视角， 以及一个不依赖会话日志、不调 LLM 就能体检 catalog 的手段。

二、解题思路

核心思想：确定性事实与 LLM 判断严格分离。 事实从日志确定性抽取、可复核可追溯；LLM 只回答一个问题——"在对话的这个决策点上，这个 skill 该不该触发？" 没有证据的判断被当作工具缺陷丢弃，而不是当作发现呈现。

五条原则，每条都是对上面某个问题的直接回应。

A1定位测量层，只读日志不插桩

asd 不进入 agent 运行路径、不注入探针。日志已落盘的事实（加载事件、usage 记录、压缩事件、prompt 哈希） 确定性抽取；日志没记录的（如"skill 被压缩挤出上下文"）绝不编造，显式标注为 inference。 代价是精度受日志所限；收益是历史会话可审计、零侵入、别人机器导出的 transcript 也能测。

A2事实 / 推断 / 判断三级标注

报告里每个结论都标来源：log fact（日志原文可核对）、inference（从事实推导，标注推导规则）、 judgment（LLM 反事实判断）。成本上估算（EST）与账单（billed）分开呈现、永不混算； 无证据的行显示 unavailable 而非 0——读者永远知道自己在看什么，数字不会被冒充。

A3证据协议

LLM 判断必须附会话原文的逐字引用；证据对不上轨迹的一律丢弃，计为工具缺陷而非发现。 这条把"判断的可信度"变成了可机械校验的东西——缺陷多时先怀疑解析器，不急着怀疑 agent。 判断层可整体降级（无凭据自动回落事实模式）、可抽样（--judge-limit），贵不贵自己控制。

A4统一 Event 模型 + 审计 IR

三种磁盘格式（Kimi CLI / 桌面版、Qoder transcript、Codex rollout）在解析层归一为同一个 Event， 下游模块只见一种形状。所有分析建立在版本化的中间表示（AuditDocument）上： 证据台账、加载链、派发链、干预标注、账单块。IR 可导出（--ir-out / --ir-analyses）， 第三方可独立复核——审计结论本身也可被审计。

A5双轴评测 + 门禁化

"遵守"拆成两个正交轴：expectations（按路由规则该消费什么）与 instruction following （规定动作执行度——带 skip 理由的跳过也计 0，因为这一轴度量执行度、不度量裁量合规，裁量合规看另一轴）。 两条轴都能变成 CI 退出码（--expect + --gate、--steps 默认门槛 0.75）， 路由回归从"感觉变差了"变成可卡住的失败。

三、能力建设

能力按管线分层：日志进来，解析归一，进 IR，一部分走确定性分析、一部分走 LLM 判断，最后渲染成交互报告。 纯标准库实现、零第三方依赖，800+ pytest 用例，测试夹具覆盖各格式会话样本。

五、边界（review 时同样重要）

  • 只读不插桩：精度受日志所限——日志不记录"skill 被丢弃"，所以挤出只能标注为推断；上下文测量、压缩事件、prompt 哈希在部分格式不可用，报告显示不可用、不用推断值顶替。
  • "加载了但内容不全 / 不对"v1 只呈现事实，不做内容级判断；"加载了但没遵守"是独立的一条轴，由 --steps 单独评估，两个分数不合并。
  • 估算不是账单：catalog 体检和六桶里的 token 数字是版本化估算器的 EST，不是 harness 的真实计费；真实计费走 opt-in 的 billed 侧通道，且永不与 EST 混算。
  • 体检不评价 agent 表现：catalog-audit 只说 catalog 的成本与缺陷；评价 agent 表现是会话审计的职责。两份报告不合并成一个分数。
  • 跨会话只有轻量 fleet 聚合，不做趋势存储与历史对比；一次深度审计仍只针对一个会话。
  • web 服务只绑 localhost、无鉴权，审计任务在内存里，重启即失（上传的会话文件持久化）。
名词表
log fact / inference / judgment
三级结论标注：日志原文可核对的事实 / 从事实显式推导并标注规则的推断 / LLM 反事实判断。
expectations
按路由规则预期被消费的 skill 清单（--expect），渲染成 loaded / file-read / MISSING 核对表。
findings
本该触发却从未加载的 skill，每条带决策点、轮次、置信度与逐字证据。
IF（instruction following）
playbook 编号步骤的执行度判定，covered / partial / skipped 加权计覆盖率。
discovery / activation
渐进式披露的两层：discovery 是常驻上下文的目录文案，activation 是按需加载的 skill 正文。
EST / billed
EST 是版本化估算器的 token 估算；billed 是 SharedClientCache 里的真实计费 token（会话级口径）。
审计 IR
版本化中间表示 AuditDocument：证据台账 + 分析产物，可经 --ir-out 导出复核。
sidechain / dispatch / orphan
子代理对话的内联记录 / 主代理派发子代理的调用 / 无法归因到派发点的子代理链。
直读（file-read）
用文件工具直接读 SKILL.md 绕过 Skill 机制——是日志事实，是否构成对正式加载的合理替代留给读者。
